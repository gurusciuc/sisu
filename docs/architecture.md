# ADR 001 · Browser engine and shell

**Decision, 16 November 2026.** Use CEF Chrome runtime with the cef Rust bindings for the feasibility build. Keep the production engine decision open until extension actions, permission prompts and tab identity pass user workflows in the custom window. Use one engine per running session.

## Evidence and alternatives

| Route | What it supplies | Integration and maintenance cost |
| --- | --- | --- |
| CEF Chrome runtime with full native engine window | Chromium networking, site isolation, JS, underlying Chrome services and native extension surfaces. The Windows reference window opened the real Proton Pass onboarding page. | Track Chromium security releases through matching CEF binaries, headers, bindings and a sandbox bootstrap. Keeping upstream controls imposes upstream UI decisions. |
| CEF Chrome runtime with native-hosted child windows | The Windows preview puts each live child in the same Rust tab order. Ordinary and lab children share their respective request context. CEF client and request-context callbacks ran before the loopback server received disallowed fixture requests. | Each hosted Chrome child has its own underlying Chromium browser window. An extension querying tabs, groups, active tab or panel ownership may observe a different topology than a user sees. Custom popup anchoring and active-tab permissions need direct validation. |
| CEF Views / Alloy style | CEF Views supplies compiled Chromium Views widgets. Chrome-style Views constrains browser-view composition. Alloy offers greater composition control. | A Chrome-style CEF Views window supports one Chrome-style BrowserView. Sharing a rendering engine alone does not demonstrate the needed permission, extension and Chrome UI services in Alloy. |
| Maintained Chromium browser fork | A fork can customize the real browser frame and keep one native TabStripModel, extension action model and side-panel host per window. | Large build and test infrastructure, upstream branch merges, platform signing, security backports, UX patch maintenance and codec distribution review. Prototype this route if the CEF tab-identity test fails. |
| Wry / system webviews | WebView2 on Windows, WKWebView on Apple platforms and WebKitGTK on Linux. Smaller distribution where the system supplies the engine. | Extension APIs, updater ownership, network hooks, storage semantics and engine behavior differ across hosts. It does not establish a single Chrome-extension platform. |
| Qt WebEngine | Chromium-based and provides native UI and a versioned extension manager. Modern Qt documents extension actions and popup pages. | Requires an explicit API, isolation, UI, license and footprint evaluation. The existence of an extension manager alone cannot settle the target matrix. |

## Windows shell

The MV3 topology fixture confirmed the child-window limitation on this host. Two visible-shell tabs report different window IDs and both appear active to the extension. This is a critical integration gate for the final foundation. See the extension-tab-topology record in evidence/windows-x64/flows.json.

Rust owns browser identifiers, selection, order, profile policy, bookmark imports, search and session preferences. Thin Win32 code draws the shell and hosts live CEF child windows. Layout moves the same views. Tab changes neither create a parallel UI runtime nor capture page snapshots. The native new-tab handoff stages the incoming child, matches its initial background to the local document and raises it before hiding its predecessor. A single one-shot timer bounds the wait for the local load notification. Tab retirement moves the approved-to-close page to a hidden teardown parent because upstream CEF posts WM_CLOSE to the root ancestor of a hosted window. This prevents an individual tab close from propagating to unrelated tabs. Web-content close requests still pass through the engine’s beforeunload handling.

Settings uses an engine history entry and an ordinary tab identifier. The shell accepts `#settings` and `browser://settings` on address-bar commit. A trusted shell-created tab can show native preference controls. External documents have no settings IPC or JavaScript bridge. Moving the tab strip reflows the viewport and can change fingerprinting measurements. The revised Windows shell uses Arial and GDI+ geometric icons to avoid installed-font variation. Screen-reader patterns, IME composition, narrow windows and mixed-DPI monitors need a wider acceptance suite.

## Security, privacy and filtering

The Windows application runs through CEF’s matching bootstrap, rejects an absent sandbox pointer, and uses the sandbox-enabled cef-rs configuration. Keep TLS, process isolation and GPU security defaults. Inspect effective sandbox policy on each target before shipping. The private launch creates a temporary root and an off-the-record request context, rejects lab extensions, denies media and site prompts, and excludes ordinary bookmark and preference files. Normal exit removes private scratch storage. Recovery after power loss needs testing. Ordinary permissions defer to Chromium prompts. The project has no telemetry endpoint. Comprehensive engine egress and third-party storage partition audits are pending. [CEF sandbox setup](https://github.com/chromiumembedded/cef/blob/master/docs/sandbox_setup.md)

EasyList and EasyPrivacy are bounded, hash-verified build inputs. adblock-rust compiles the rules once during the build. Runtime hooks classify source, resource type and method. The tests cover controls, subframes, redirects, dedicated-worker and service-worker fetches. Host-specific cosmetic hiding runs at frame load end. Generic cosmetic selectors, earlier document injection, CSP interactions, service-worker cache hits, WebSockets, scriptlets, and explicit surrogate resources need more work. Production list updates require verified signatures, validation and a previous-good generation, with measured peak memory. [adblock-rust](https://github.com/brave/adblock-rust) · [CEF resource request hook](https://github.com/chromiumembedded/cef/blob/6028375/include/cef_resource_request_handler.h)

Privacy validation should compare observed cookies, caches, storage, screen, fonts, time, language, timers, canvas, graphics, DNS, WebRTC and proxy behavior to an explicit per-profile policy. Condition results on the browser actually providing the capability under test. Chromium’s upstream defenses and private cookies alone do not demonstrate Mullvad-equivalent anonymity. [Mullvad Browser reference](https://mullvad.net/en/browser/hard-facts) · [PrivacyTests methodology](https://privacytests.org/about.html)

A custom Rust renderer is a separate research project. Switching engines requires matching web-platform, site compatibility, security, extension, input, accessibility and memory benchmarks. The preview loads no second engine.
